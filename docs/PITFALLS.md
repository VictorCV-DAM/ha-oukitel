# Pitfalls and runbook

This is the list of traps found while bringing up the zero-cloud branch. Each
entry describes the symptom, the cause and what to do.

## 1. Tag 11: port or timeout?

**Symptom:** `0x7010` is accepted but the station never connects, or it stays
at `0x7014` 49.

**Cause:** the app builder names tag 11 `time` and its callers pass a timeout.
On this firmware, the value that made the station connect was the **port**
(`8886`/`8883`); sending `60` did not.

**What to do:** try the port value first. If a future firmware behaves
differently, log `0x7011`/`0x7014` and compare. Do not treat either meaning as
universal.

## 2. MCC is not the confirmed blocker

**Symptom:** after a factory reset, the station does not join Wi-Fi with
MCC 460.

**Cause:** the real blocker was a **stale Wi-Fi password**. MCC 460 vs 214 was
never isolated with the correct password.

**What to do:** always use the current Wi-Fi password. Change MCC only as an
experiment and log both cases.

## 3. Stale Wi-Fi password

**Symptom:** the station never joins; `0x7014` 49 forever.

**Cause:** the integration or a script reused an old password after the Wi-Fi
changed.

**What to do:** enter the password again, character by character, and verify
the SSID is 2.4 GHz.

## 4. `0x7010` only works on a virgin/reset device

**Symptom:** `0x7010` is acknowledged but the endpoint does not change.

**Cause:** the module ignores endpoint changes while it is bound/online.

**What to do:** use the Wonderfree “restore factory values” option, then
provision again. There is no local shortcut.

## 5. `0x7055` needs a reset certificate

**Symptom:** the reconfiguration frame is ignored.

**Cause:** `0x7055`/28757 requires the cloud-issued reset certificate.

**What to do:** do not send it without the certificate; use a factory reset
instead.

## 6. The BLE window is fixed

**Symptom:** telemetry stops ~3 minutes after provisioning.

**Cause:** the module closes BLE ~200 s after `0x7010`; the MCU then cuts the
UART stream.

**What to do:** keep the BLE session open while testing. Re-open the window
with the IoT button for another ~3 minutes.

## 7. Keepalive does not extend the window

**Symptom:** `BLE_KEEPALIVE_TICK` at +10 s and +20 s, disconnect at +21 s.

**Cause:** the window is tied to the pairing state, not to write inactivity.

**What to do:** do not rely on keepalive. Design around the window or use
hardware access.

## 8. `0x7066` is an empty ack

**Symptom:** sending tags or `0xFFFE` in `0x7066` does not bind the station.

**Cause:** the app sends an `emptyList()`; the app ignores `0x7014`; `0xFFFE`
is generated by the module after the cloud bind.

**What to do:** do not fabricate bind acks. The bind must come from the vendor
cloud or from the module's own state.

## 9. LAN is gated by the cloud

**Symptom:** LAN telemetry stops when the WAN is cut.

**Cause:** the station's LAN service depends on the vendor cloud session.

**What to do:** keep the cloud link alive for LAN, or use the BLE-tethered
local mode with its ~3-minute window.

## 10. `authKey` changes after reset/rebind

**Symptom:** LAN login returns `-1`.

**Cause:** the cloud issued a new `authKey`; the integration cached the old one.

**What to do:** fetch `userDeviceList` again and update the entry. The clean
proposal includes an automatic refresh, but it is not in this branch.

## 11. The PSK is not in the app, API or OTA

**Symptom:** all TLS-PSK candidates fail.

**Cause:** the PSK is a per-device secret in the module NVM.

**What to do:** stop guessing. The remaining routes are UART/JTAG, a hardware
BLE sniffer, or vendor documentation.

## 12. OTA has no plan for this device

**Symptom:** `getBatchDeviceUpgradePlan` returns `data: []`.

**Cause:** no firmware plan is assigned to the device.

**What to do:** do not expect a firmware download. The PSK is not in the image
anyway.

## 13. Do not blind-fuzz `9c40`

**Symptom:** unknown commands can leave the module in DFU, erase its
configuration or brick it.

**Cause:** `9c40` is the provisioning/OTA channel, not a debug port.

**What to do:** only send documented/known read commands, preferably on a
bench unit. Never fuzz the live roof unit.

## 14. Test services are not production features

**Symptom:** `ble_disconnect`, `bridge_send` and the TLS probe on `18883` are
exposed.

**Cause:** they are diagnostics from the test work.

**What to do:** do not use them in production. Remove them before a stable
release.

## 15. HA restart drops the BLE client

**Symptom:** after a restart, the station reconnects to the broker but does
not publish.

**Cause:** the BLE client is lost; the module needs a new pairing window.

**What to do:** press the IoT button and run the BLE provisioning again.

## 16. Entities can show stale values

**Symptom:** battery or power values remain after the station stops streaming.

**Cause:** LAN/bridge state is cached; the station is offline but the entity is
not marked unavailable immediately.

**What to do:** check the connection-mode/online diagnostic and the log, not
just the entity value.

## 17. No-endpoint mode

**Symptom:** the station joins Wi-Fi but has no cloud/broker connection.

**Cause:** this is expected with endpoint `none`/`lan`; it opens LAN `6607`.

**What to do:** use it only for LAN tests; the cloud binding and the Wi-Fi icon
will not be fixed.

## 18. Hardware safety

**Symptom:** opening the unit or probing UART/JTAG risks short circuits and
high voltage.

**Cause:** the station has a battery and an inverter.

**What to do:** use a bench unit, isolate the DC/AC inputs, and never probe a
live roof installation without a safety plan.

## 19. Two “starting LAN session” log lines in a row

**Symptom:** the log shows the same block twice, a few seconds apart:

```text
oukitel: Using configured static host 192.168.1.15 for LAN connection
oukitel: Device found at 192.168.1.15 — starting LAN session
oukitel: LAN login OK! Handshake succeeded with 192.168.1.15
oukitel: LAN session established and active with 192.168.1.15!
```

**Cause:** these are two **separate** `async_setup_lan()` calls, not a
duplicated log line:

1. The first comes from `__init__.py` during setup (offline boot loop or a
   background task).
2. The second comes from `_async_update_data` in `auto` mode. When the previous
   socket has dropped, `_lan_active` is `False`, the listen task is done, and
   `_LAN_RETRY_INTERVAL` (20 s) has elapsed, the coordinator starts a new
   attempt.

The previous socket is usually dropped because the station closes its LAN
service when it cannot complete the vendor cloud bind. The disconnect is logged
at `DEBUG`, so it is not visible at the default level and the second block looks
like a duplicate.

**Is it a bug?** No, as long as the first session is gone before the second
starts. The `_lan_setup_in_flight` guard prevents two setups at the same time.
A real bug would be two **simultaneous active** LAN sessions; you can rule that
out by checking for a disconnect or a new `LAN_HANDSHAKE` before the second
block.

**What to do:**

- Nothing, if the second attempt connects and telemetry works.
- To reduce noise, use `connection_mode = lan` (the `_async_update_data` retry
  block only applies to `MODE_AUTO`), or fix the vendor bind so the station
  keeps the LAN socket alive.
- When reporting a problem, include both blocks and the lines between them; the
  disconnect is the important part.
